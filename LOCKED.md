# This app is locked

`docs/play/` is **hand-built and hand-maintained**. It has no build step, no
bundler, no package manager and no dependencies, and it must stay that way.

## What that means in practice

- **No CI, no build workflow, no release pipeline.** There is deliberately no
  `.github/workflows/` in this repository. Adding one that rebuilds, minifies or
  regenerates `docs/play/` defeats the point: the file in the repo is the
  artefact, and it is the only artefact.
- **No packaging.** This reader is not compiled into a Windows EXE, an Android
  APK or a Linux binary, and it is not wired into `app-builder` (the estate's
  forge). It is a web page served as a page. If a binary is ever wanted, that is
  a separate product with its own repository, not a build of this one.
- **No automation touches the design.** Tools that rewrite markup, inject a
  banner, swap a palette or "optimise" the CSS are out of scope here, however
  well they behave elsewhere in the estate.
- **Changes are made by hand, in a small diff, and looked at afterwards** — in
  both themes, at desktop and phone width, with the connection on and off.

## Why

The reader is a single file whose whole value is that it can be read, audited
and repaired by a person. Every generated byte makes that harder, and a build
pipeline would let a routine run silently replace the design with something
nobody looked at. The library it reads is versioned and rebuilt by scripts; the
reader that reads it is not.

## What is allowed

- Editing `docs/play/index.html`, `sw.js`, `manifest.webmanifest`, `icon.svg` by hand.
- Regenerating the screenshots in `docs/assets/` after a deliberate change.
- Bumping the service-worker `CACHE` string and the build stamp in the landing
  footer, on every release.
- Fetching the library from GitHub at runtime — that is the app's whole data path.

If a change cannot be made without a build step, the change is wrong.
